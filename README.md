# MoonBit 生态索引

按使用场景组织的 MoonBit 包索引。本项目采集 mooncakes.io 注册表的公开数据，将包归入
37 个常见技术场景，并把有完整方案的场景划分为**完整方案**与**基础库**两个层级，生成一份
可在浏览器中检索的静态站点。

本项目定位是**导航**，不是注册表的替代品。包的版本历史、完整 API 文档与依赖关系不在
本站复制，页面内每个包名都直接指向 mooncakes 包页，需要细看时点过去即可。

站点为纯静态产物，构建在本地完成，可托管于 Cloudflare Pages、GitHub Pages 或任意
静态文件服务。

---

## 一、数据时效

本索引是**离线快照，不随注册表实时更新**。

| 数据项 | 来源 | 快照时间 | 是否对外 |
| --- | --- | --- | --- |
| 模块元数据（名称、版本、描述、关键词、许可、仓库、yanked） | mooncakes.io 官方 API | 2026-11-02 | 是 |
| 下载量 | mooncakes.io 官方 API | 2026-11-02 | **否**，仅参与构建期排序 |

站点顶部与页脚均标注两项时间：**采集**（快照日期）与**构建**（页面生成时间）。所有数据
均早于构建时间，注册表在此之后的变动不在本站范围内：

- 快照之后发布的包不会出现在本站；
- 已发布新版本的包，其版本号与描述可能滞后；
- yanked 状态以快照时为准（当前 96 个），检索页标注 `[yanked]`，且不进入场景推荐。

对时效敏感的选型判断，应回到 mooncakes.io 与仓库实际状态核实。如需刷新，依照
「五、数据更新」重新抓取并构建。

## 二、分层口径

同一场景内混列「可承担项目骨架的包」与「提供单点能力的包」，会使选型失去意义，因此
本索引将候选分为两层；**没有完整方案的场景不设分层**，那里的候选全部是基础库，
站内不再分出空的「完整方案」组。

| 层级 | 判定标准 | 示例 |
| --- | --- | --- |
| **完整方案** | 定义程序结构，由调用方填空：路由表、组件树、事件循环、ECS、数据访问层、命令行树、语法 DSL、测试容器 | `moonback`、`rabbita`、`proton`、`selene`、`moondb`、`ArgParser` |
| **基础库** | 提供单点能力，由调用方组合：格式解析、哈希、C 库绑定、数据结构 | `yaml`、`sha256`、`btree`、`sqlite`、`gtk`、`glfw` |

框架、引擎、运行时、脚手架、ORM 均属「完整方案」的不同形态。

需特别说明：**「基础库」不等同于「依赖」**。在 mooncakes 生态中，完整方案本身同样是依赖
（`moon.mod.json` 的 deps 收录全部包），因此以 deps 作为「方案」的反义词在定义上不成立。
分层的唯一标准是该包能否接管程序结构。由此可推出：所有 binding 均归入基础库，完整方案
位于其上层（`giraffe` 之于 GTK，`proton` 之于 WebView）。

完整方案的判定**采用人工白名单**（`pipeline/analyze.py` 中的 `SOLUTIONS`，当前 71 个包），
不使用启发式推断。方案层是高精度区，宁可遗漏，也不将基础库纳入推荐位。构建脚本每次运行
会输出「待确认的方案候选」，即自我描述含 `framework` 等字样、尚未收录白名单的包，供人工
复核后补入。

37 个场景中，15 个存在完整方案；其余 22 个（graphics、img、media、httpc、net、proto、json、
binfmt、compiler、regex、unicode、hash、cipher、encode、archive、fs、math、ds、tool、doc、
time、log）在生态中尚无框架或引擎级实现。这些场景在站内只有一个基础库清单，并注明「尚无完整
方案，需按需组合」，不去虚构一个空的方案组。这属于生态现状，而非数据缺失。

### 场景粒度

场景按「一个开发者的一次决策」划分，而不是按包的实现方式。粗粒度的场景无法给出可操作的建议：
把 JSON、YAML、CBOR 混在一个清单里，选型时仍要自己逐条筛。因此对原先过粗的场景做了拆分：

| 原场景 | 拆分后 | 依据 |
| --- | --- | --- |
| JSON / 序列化格式 | JSON 解析、配置 / 标记格式、二进制编码 | 文本格式、配置语言、二进制编码是三类不同的选型 |
| 加密 / 哈希 / 编码 | 哈希 / 校验、加密 / 签名、编码 / 转义 | 校验完整性、保证机密性、字节转文本，用途互不替代 |
| 图像 / 媒体 | 图像编解码、音频 / 视频 | 图像处理与音视频播放/采集没有交集 |
| 网络 / 协议 | 网络传输 / 套接字、应用协议 / RPC | 传输层选型与协议栈选型是两个问题 |
| Web 后端 / HTTP 服务 | 服务端框架、HTTP 客户端 | 写服务端与调别人接口，候选几乎不重合 |
| 解析器 / 编译器 / 语法 | 解析器 / 语法、编译器 / 代码生成 | 把文本读成结构，与把结构变成可执行物 |
| CLI 参数解析 | 同上（加了 core 门控） | 原先 221 个候选里大量是「带 CLI 的应用」，收紧到 86 |

拆分的代价是场景数量变多（29 → 37），但每个清单的可信度更高。合并与拆分都只依赖关键词与
人工白名单，没有引入新的判定机制。

### 场景归属：覆盖即出现

一个包若同时胜任多个场景，就在每个场景里都出现，不设「主场景」独占。例如 `moui` 既在
桌面（macOS / Windows / Linux 主线）也在移动端（HarmonyOS 已承诺，Android / iOS 实验性），
`moonbit-community/pty` 同时出现在终端 UI、异步与运维三个场景。多数场景由关键词自动判定，
因此天然支持多归属；移动端与运维为人工清单，需人工维护多归属关系；桌面以关键词判定为主，
少数元数据命不中的包由 `force` 显式兜底。

为避免人工清单长期漏收，`pipeline/analyze.py` 为这类场景声明了 `audit` 复核词，构建时扫描
全量模块，命中却未收录的包会打印成「人工场景的覆盖缺口」；确认不收的包记入 `skip` 并写明
理由，使排除决定同样可追溯。

## 三、站点结构

站点为单页应用，路由由 URL hash 承担，共三个视图：

| 视图 | 地址 | 内容 |
| --- | --- | --- |
| 首页 | `#/` | 全部 37 个场景卡片，按「界面与应用 / 服务与数据 / 语言与工具」三组排列 |
| 场景详情 | `#/s/<场景 id>` | 该场景的完整清单，完整方案与基础库全部列出，不截断 |
| 检索 | `#/search` | 全量 3520 个模块的名称与描述检索 |

首页每个场景卡片：

- 标题后为**完整方案 / 基础库**切换标签，点击即切换，不再使用折叠展开；
- 列表区**固定为 5 行的高度**，超出部分裁掉，卡片底部提供「查看全部 N 个」入口；
- 卡片本身跳转到站内详情页，包名才跳转到 mooncakes 包页。

左侧分类导航常驻，独立滚动，与右侧内容区互不影响；滚动时不随内容移动。窄屏下改为
**抽屉式导航**：标题栏左侧提供菜单按钮，点击后侧栏自左滑出，带半透明遮罩，可点遮罩、
关闭按钮或按 `Esc` 收起；选中场景后自动收起，不遮挡新页面。

### 反馈入口

标题栏右端的 GitHub 图标在任何一个视图里都可点，指向本仓库；页脚末尾的「反馈与勘误」
一段则把仓库地址与 `issues/new` 以文字链接写出，便于复制与转述。两处地址都由
`pipeline/analyze.py` 顶部的 `REPO` 生成——构建时写入 `dist/assets/app.js` 与
`dist/index.html`，改地址只需改这一行，不会出现两处不一致。

反馈时给出一个包名即可定位规则：场景的判定词、显式收录（`force`）、排除项（`ex` /
`ex_desc` / `ex_prefix`）与整族排除（`GLOBAL_EXCLUDE_PREFIX`）都在 `analyze.py` 里。

### 语言

中英文由三层决定，优先级从高到低：

1. URL 的 `?lang=zh` / `?lang=en`——带参数的链接本身就是「这个语言版本」，可分享；
2. 上次手动切换的选择（`localStorage`），从无参数链接进来时沿用；
3. 浏览器首选语言 `navigator.languages[0]`：以 `zh` 开头显示中文，其余一律英文。

标题栏右端有切换按钮，按钮上写的是**点它会切到的语言**：中文界面显示 `EN`，英文界面
显示 `中文`。点击即时生效，不重载页面——只重建文案、侧栏与当前视图，检索页会保留当前
查询；同时把选择写回 URL 与 `localStorage`。

双语不是两套页面：

- 场景的 `title` / `intro` / `note` 在 `dist/data/scenarios.json` 中为 `[中文, 英文]`
  二元数组，前端按语言取下标；中文原文仍写在 `pipeline/analyze.py` 的 `SCENARIOS` 里。
- 英文译文集中在 `data/i18n.json`，构建时按场景 id 合并。少一条译文、或留下一个
  `SCENARIOS` 里不存在的 id，`analyze.py` 会直接构建失败——不会带着漏译上线。
- 界面文案（按钮、页脚、检索提示）在 `dist/assets/app.js` 的 `T` 表，中英各一份，
  静态骨架通过 `data-i18n` 属性填充，`<html lang>` 与 `<title>` 同步切换。
- 包描述来自注册表原文（多数为英文），不翻译：它是元数据，不是本站的表述。

## 四、目录结构

```
.
├── pipeline/
│   ├── analyze.py            数据合并、场景打分、排序与产物生成
│   ├── query.py              命令行查询（场景 / 全量检索 / SQL）
│   ├── og.html               分享卡片源文件（1200×630，headless 截图用）
│   └── make_assets.py        生成分享卡片与站点图标（手动执行，不参与日常构建）
├── data/
│   ├── raw/                  原始快照，只增不改，用于复现
│   ├── i18n.json             场景与分组的英文译文（构建时校验完整性）
│   ├── modules.json          合并后的模块表（3520 条）
│   ├── scenarios.json        站点数据源（含精简模块表与场景清单）
│   └── moonbit_index.db      SQLite 索引（modules / scenarios 两表）
├── dist/                     静态发布目录（产物入库，便于直接部署与差异追溯）
│   ├── index.html            骨架，仅有样式与容器，不含数据
│   ├── assets/app.js         前端逻辑（路由、渲染、检索）
│   ├── data/scenarios.json   全部数据
│   ├── og.png                分享卡片（og:image / twitter:image）
│   ├── favicon.ico           16/32/48 图标（另见 assets/favicon.svg）
│   ├── apple-touch-icon.png  180×180，iOS 添加到主屏
│   └── scenarios.md
├── scenarios.md              场景推荐报告（Markdown，便于引用于文档）
└── README.md
```

`dist/` 内文件均由 `pipeline/analyze.py` 生成，不应手动修改。

页面与数据彻底分离：`index.html` 约 9 KB，只含 CSS 与挂载点；数据全部在
`dist/data/scenarios.json`，由前端 `fetch` 加载。因此改样式不必重新生成数据，更新数据
也不必重写页面。

## 五、构建与部署

### 构建

```bash
python3 pipeline/analyze.py
```

脚本读取 `data/raw/` 与 `data/` 中的既有数据，输出四类产物：SQLite 索引、Markdown 报告、
站点数据 JSON，以及 `dist/` 站点。运行环境仅需 Python 3.9 及以上，无第三方依赖。

### 部署至 Cloudflare Pages

产物是纯静态文件且已随仓库提交，因此有两种方式，选一种即可。

**方式一：Git 集成（推荐，push 即发布）**

1. Cloudflare 控制台 → Workers & Pages → 创建 → Pages → 连接到 Git，授权并选中本仓库；
2. 分支选 `main`，框架预设选 `None`；
3. **构建命令留空**，**构建输出目录填 `dist`**；
4. 保存并部署，站点落在 `moonbit-ecosystem-index.pages.dev`。

之后每次 `git push` 都会自动发布一次新产物，云端不执行任何构建。

**方式二：本地直传**

```bash
npx wrangler pages deploy dist --project-name moonbit-ecosystem-index
```

首次运行会打开浏览器完成 Cloudflare 授权，并自动创建同名项目；`wrangler.toml` 里的
`pages_build_output_dir` 已指向 `dist`。

本项目未采用「在 Cloudflare 上运行构建脚本」的方式：Pages 的构建镜像以 Node.js 为主，
Python 可用性不作保证；而站点产物为纯静态文件，本地构建后上传即可满足需求，无须为此
引入额外的 Node 构建链。若确实需要云端重建（例如以后加定时抓取），把构建命令改为
`python3 pipeline/analyze.py` 即可——`data/raw/` 已在仓库内，脚本无第三方依赖。

### 分享卡片与站点图标

链接被分享到微信、Discord、Slack、X 时显示成什么样，由 `<head>` 里的 `og:` 一组标签决定。
抓取方不执行 JavaScript，所以这组标签是**静态中文默认值**，站内的语言切换不会改动它们。

```bash
python3 pipeline/make_assets.py     # 仅在改配色、改文案或换域名后需要重跑
```

| 产物 | 用途 |
| --- | --- |
| `dist/og.png` | 1200×630 分享卡片，`og:image` 与 `twitter:image` |
| `dist/assets/favicon.svg` | 矢量图标，现代浏览器优先使用 |
| `dist/favicon.ico` | 16/32/48 三档，兜住旧客户端与对 `/favicon.ico` 的硬请求 |
| `dist/apple-touch-icon.png` | 180×180，iOS 添加到主屏 |

`make_assets.py` 不参与日常构建，也不在 `analyze.py` 的调用链里：这些产物已入库，只有内容
变了才需要重跑。它依赖 Pillow（画图标）与本机 Chrome（把 `pipeline/og.html` 截成卡片）；
缺 Chrome 时只更新图标、卡片保持原样，不会留下半张图。卡片本身是 `pipeline/og.html`，
改文案直接改这个文件，比改 Python 里的字符串直观。

换域名时要改 `pipeline/analyze.py` 顶部的 `SITE`：`og:url` 与 `og:image` 必须是绝对 URL，
抓取方不解析相对路径，改漏了分享出去的卡片就是空白。

### 本地预览

```bash
python3 -m http.server 8000 --directory dist
```

访问 `http://localhost:8000`。

**必须通过 HTTP 打开**：数据由前端 `fetch` 加载，直接双击以 `file://` 打开会被浏览器
的同源策略拦截，页面会提示加载失败并给出上述命令。

## 六、数据更新

1. 抓取 `https://mooncakes.io/api/v0/modules`，写入 `data/raw/modules_api.json`；
2. 通过 `https://mooncakes.io/api/v0/search?kw=<关键词>&limit=100` 补齐下载量，写入
   `data/raw/downloads.json`。该接口单次上限 100 条且不支持分页，需以「关键词并集」加
   「包名精确检索」两步合并，方可覆盖全量。**该文件只用于构建期排序，不复制进 `dist/`，
   也不写入站点数据**；若跳过此步，构建会退化为仅按关键词排序，清单质量明显下降
   （`moonback`、`rabbita` 等会掉出前六），不建议省略；
3. 修改 `pipeline/analyze.py` 顶部的 `COLLECTED_AT` 为本次采集日期；
4. 运行 `python3 pipeline/analyze.py`。

## 七、命令行查询

```bash
python3 pipeline/query.py --list                    # 场景清单与两层计数
python3 pipeline/query.py http                      # 指定场景的完整方案
python3 pipeline/query.py "移动端"                   # 支持中文场景名
python3 pipeline/query.py http --libs --top 20      # 连同基础库一并展开
python3 pipeline/query.py --search websocket        # 全量检索模块
python3 pipeline/query.py --sql "select name,downloads from modules order by downloads desc limit 10"
```

命令行是维护工具，读取本地 SQLite，其中保留了下载量原始值（用于比对排序是否合理、
排查场景归属）。站点产物不经过它，也不含该字段。

## 八、排序方法

```
score = min(关键词匹配度, 6) × 1.0
      + log(1 + 下载量) × 1.35
```

只使用两项信号：与场景的关键词相关度、注册表内的下载量。**不引入反向依赖数、传递依赖数
等派生指标**——本站只做导航，派生指标既扩大数据滞后面，也容易把「被依赖得多」误当成
「适合这个场景」。

关键词匹配依据 `keywords`、包名词元与描述词元，并做词干前缀归一（使 `async` 命中
"Asynchronous"、`argparse` 命中 `ArgParser`）。易混场景设有排除规则，例如 UI 场景排除
TUI、文档场景排除 UI 框架。db、net、gui、archive、fs、tool 等场景另有少量人工置顶，用于
纠正「接口库排在使用库之前」的偏差。

仅纳入下载量大于 20 的模块（3520 个中的 3341 个），yanked 包不进入推荐。

关键词命不中、但人工确认属于该场景的包记在 `force`，按**其所属层级的中位分**安置：
既不因为手工收录而占据前列，也不因为描述缺失而沉到末尾；需要更靠前时用 `pin` 明说。

两个容易漏收的边角，已在评分里单独处理：

- **包名精确命中算强信号**。注册表里不少包的关键词与描述都是空的（`moonbit-community/yaml`、
  `moonbit-community/sqlite3`、`Milky2018/gamepad`），名字是唯一线索。名字里出现与场景词完全
  相同的词（长度 ≥3）即按强命中计，但 `net`、`map`、`ui`、`test` 这类太泛的词列在
  `AMBIGUOUS_NAME_TOKENS` 里不享受此待遇——`moonxi-net` 是深度学习框架，`test_postadd`
  是作者的发布探针，都不该因此被收进来。
- **整族排除**。`cli/*`（MoonX 复刻的 coreutils，一条命令一个包）与 `gmlewis/fonts-*`
  （按字母切分的字体数据分片）不进入任何场景：它们的关键词覆盖 command-line / json / hash /
  base64 / svg，会同时污染六七个场景，而单个包并不构成一个可选型的库。

### 为什么站内不展示下载量

早期版本的每一行右侧都挂着下载量（`7.5k`、`20.1万`），同时在行首标出序号。两个数字并排
出现时，读者必然逐行比对，而序号来自加权分，不可能与下载量同序——**37 个场景里，28 个
场景的区块前 5 名存在「后面的包下载量更高」的情况**。例如桌面场景的完整方案，下载量序列是
26810 → 1797 → 99 → 452 → 160 → 282。列表因此在最显眼的位置自相矛盾，看起来像排序坏了。

三种处理方式里，最终选择把下载量移出对外产物：

| 方案 | 结果 |
| --- | --- |
| 全员改为按下载量排序 | 名次与下载量恒等，但 8 个区块会被 `mizchi/x`、`moonbitlang/x` 这类万能包占据第一，`moonback`、`rabbita` 等会掉出前六 |
| 保留加权序、去掉序号 | 不再自相矛盾，但顺序仍无法被读者核验 |
| **下载量只在构建期排序，不进产物**（当前） | 顺序保留推荐质量，页面上不存在第二个数字，无从比对；`scenarios.json` 里也没有这个字段 |

因此：站点数据只有一份事实性来源（模块元数据），下载量退化为一个不公开的量级因子。
前端拿不到这个数字，也就没有再次把「流行」误读成「适合」的可能。选型要看的是 API 形态
与维护状态，这两项本就该到包页自行核对。

## 九、已知局限

1. **排序含有一个本站不展示的量级因子**：下载量为累计值，不反映近期热度，发布较早的包
   在同等相关度下天然占优。该因子只影响顺序、不出现在页面上，读者无法逐行核验，
   这是为提高推荐质量而做的取舍；可核验的部分是场景归属、层级划分与包页链接。
2. **约 386 个包无描述、680 个无关键词**，仅能依据包名匹配，存在遗漏可能。
3. **场景划分为人为定义**，并非生态固有分类；同一包可能适用于多个场景。
4. **完整方案判定为主观白名单**，边界情形（如 `mizchi/tui` 计入方案而 `tonyfettes/xml`
   不计入）存在判断空间。代价是新发布的方案需人工补入方可出现在方案层。
5. **基础库层未再细分**，目前未区分完整工具（如 `cmark`）与底层原语（如 `sha256`）。
6. **桌面与移动端两个场景为人工圈定**：生态中既没有 `desktop`/`mobile` 这种可靠关键词
   （`mobile` 会被三端窗口库命中，`ios` 会命中 `versions`），也无法靠描述区分，因此候选
   清单与顺序由人工确定，其 `score` 字段为优先级序号而非算法得分。多归属关系同属人工
   维护，靠构建时的 `audit` 复核词兜底提示。
7. **运维场景为人工圈定**：生态中的运维能力分散在伪终端、子进程、系统指标等单点库里，
   没有框架级实现；进程管理器与 CI 运行器属可整件部署的成品，单列为完整方案，其余按
   基础库列出供组合。
8. **部分场景基础库候选偏多**（wasm 303、parser 227、fs 122、graphics 123），源于关键词宽泛，未做进一步
   收敛；详情页完整列出，首页仅显示前 5 个。
9. **`moonbit-community/window` 在注册表中已不可用**，现行为 fork 版 `wzzc-dev/window`；
   `Milky2018/window` 为另一条独立实现。
10. **`Yoorkin/rabbit-tea` 已被 yanked**，TEA 路线的现行实现为 `moonbit-community/rabbita`。
11. **新包在排序中系统性偏弱**：`log(下载量)` 权重最高，而下载量为累计值，刚发布的包难以
    与老包比较。`created_at` 系注册表收录时间而非项目起始时间，无法据以计算增长速度，
    因此只能对部分框架级包（`proton`、`moui`、`native-gui`）人工加权。该偏差只体现在
    顺序上，站内不展示下载量，读者不会被一个数字误导；但顺序本身确实带有这个偏好。
