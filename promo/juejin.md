# MoonBit 已经有 3520 个包了，但没人告诉你该用哪个

MoonBit 这两年长得比很多人以为的快。

这份索引的数据采集于 11 月 2 日，mooncakes 上已发布模块 3520 个。桌面、移动端、Web 框架、终端 UI、游戏引擎、HTTP 服务、数据库、LLM、微信小程序、鸿蒙……该有的基本都有了，有些方向还不止一个方案。

问题是：除了包作者自己，没多少人知道它们都在那儿。

## 一、包不少，但找不着

起因很简单：想用 MoonBit 写个桌面小工具，打开 mooncakes 搜 `gui`。

出来一屏包。有底层窗口绑定，有 WebView 封装，有完整的应用框架，全混在一起排着。没有分类，没有层级，只有名字和一句话描述。

你得把每个 README 点开读一遍，才能判断「这个能不能当骨架用」。读了半个下午才明白，这本来不该由使用者来做。

这不是 mooncakes 的问题。注册表负责登记：有哪些包、什么版本、依赖谁。它不负责回答「我想做 X，该用哪几个」——那是选型，是另一件事。

而选型这件事，在包的数量过了三位数之后，就没人能靠翻 README 做完了。

## 二、做了什么

把 3520 个模块按**使用场景**重新排了一遍，37 个场景，覆盖从桌面到 WebAssembly 互操作。

每个场景里的包分两层：

- **完整方案**：能直接选型、定骨架的。框架、引擎、运行时、脚手架、ORM 都算。
- **基础库**：提供单点能力，由调用方自己组合。

37 个场景里 15 个有完整方案，一共 71 个包。剩下 22 个场景还没有框架级实现，那里的候选全部是基础库，就不硬分出「完整方案」这一栏。

这 71 个方案，每个配了一句简介。不是注册表里那句英文描述，而是回答：它是什么形态的方案、它替你做了哪些决定、什么情况下该选它。

下面挑几个场景展开。完整清单在站点上。

## 三、生态已经长到什么程度

### 桌面：四条路线，区别在于谁负责画

桌面是最早想解决的场景，也是最能说明问题的一个。这个方向上现在同时跑着四种路线，差别可以归结成一个问题：**谁负责把界面画出来。**

**浏览器画。** `proton` 用内置浏览器渲染，能直接复用前端技术栈，托盘、剪贴板、全局热键这些系统模块都配了；`orbit` 用系统 WebView，IPC 带策略授权，另附一套 orbit-cli 工具链；`lepus-apps/webview` 更彻底，界面层完全交给 HTML/CSS，MoonBit 只管窗口与系统调用。

**框架自己画。** `moui` 自带渲染引擎，既不依赖系统 WebView，也不依赖系统渲染，桌面和移动共用一套代码，渲染行为由框架自己控制。

**系统画。** `native-gui` 不带渲染引擎，界面交给系统渲染引擎绘制，一套代码生成 Windows、Linux、macOS 窗口，托盘、通知这些系统能力内置。

**系统控件画。** `giraffe` 绑 GTK4，界面由 GTK 现成的原生控件构成，走 Elm 架构。

四条路的代价不一样：浏览器画能复用前端生态，但产物重、启动慢；框架自己画最可控，但控件要自己长；交给系统画最贴平台，跨平台一致性由系统保证，代价是渲染细节不可控。

第七个 `lepusa` 是研究性实现，可作为架构参考。

一个方向上有七种选择，说明生态已经过了「有没有」的阶段，开始有「选哪个」的烦恼了。

### HTTP：13 个框架，几乎把主流设计搬了一遍

这是竞争最充分的地方。官方的 `moonback` 是默认底座，路由、中间件、请求响应抽象都齐。

其余十二个有意思的地方在于，它们几乎覆盖了当下所有主流框架的设计思路：`kupas/express` 直接对标 Express，底层走 uWebSockets；`mizchi/mars` 和 `anccnuer/onho` 是 Hono 风格，trie 路由加 SSE；`RabitLogic/mbit` 学 Gin；`KKKIIO/moondark` 学 Django，建在 moonback 上还带工程结构约定；`wflixu/Halo` 用 Koa 的洋葱模型；`jaredzhou/pony` 是 Go 的 Chi 那一路。

另外五个各占一个位置：把路由、参数、响应都纳入类型检查的 `moonapi`，同工程组织前后端的 `moonway`，面向多服务拆分的 `moonzero`，接口接近 Express 的 `mocket`，以及出自 MoonBit 语言作者之手、偏探索性质的 `crescent`。

从 Web 转过来的人基本能找到自己熟的那一套，迁移成本主要不在框架，在语言本身。

### 小程序：官方没覆盖的地方，社区补了四套

这个场景值得单独说，因为它是社区在填空白。

微信小程序的 Skyline 渲染引擎，现在有两套 MoonBit 实现：`minimoon` 和 `lampo`，都是 Elm 风格，区别在状态管理——前者用事务性的局部状态更新，后者干脆不要全局 store，状态按组件隔离。

`moon-miniprogram` 走的是另一条路，做完整开发框架：类型安全运行时、状态自动 diff、跨页 store、声明式路由。`bunnia` 则把平台适配做成可插拔的，用一套代码走多端小程序。

鸿蒙那边有 `moonohos`，解决异步任务、平台模块调用与 HAR 打包。

一个平台出现三四种互不相同的实现，通常意味着需求已经明确、但还没有形成标准答案。

### LLM：五个方案，形态完全不同

LLM 是最近长得最快的一类，但这里没有出现「大家都做同一件事」的情况。

`posoco` 是六边形架构的 Agent 框架，`mcp` 是类型安全的 MCP SDK，服务端客户端都有，`weopqrst/agent` 把 LangChain 的核心搬了过来，`golem_sdk` 绑定 Golem 平台做可持久化 agent，`moonlm` 更彻底，直接做本地推理引擎，不依赖外部 API。

同一个方向上五种不同的切入点，说明这里还没有共识，也说明现在入场还不算晚。

## 四、还有 22 个方向没有框架级实现

37 个场景排完，最有用的信息不是「有哪些包」，而是「哪些地方还是空的」。

下面这 22 个方向，目前没有任何框架、引擎或运行时级的实现，全是需要自己拼的基础库：

图形渲染、图像编解码、音视频、HTTP 客户端、网络传输、应用协议与 RPC、JSON 解析、二进制编码、日志与追踪、文件与路径、数学与数值计算、数据结构与算法、开发工具、Markdown 与文档转换、时间日期、Unicode 文本处理、哈希校验、加密与签名、编码转义、压缩归档、编译器与代码生成、正则匹配。

这份名单换个角度看就是机会清单。比如 JSON 解析有 119 个基础库，却没有一个能当骨架用的方案；图形渲染有 101 个，同样没有。这些数字说明有人在等，也说明有人在重复造。

## 六、做法与局限

最后交代一下这份索引是怎么来的。

模块数据取自 mooncakes 官方 API，场景划分、分类规则、排序与页面构建由脚本完成；各场景的组织方式与包简介的初稿借助 AI 起草，之后逐条调整措辞。

需要说明的是，71 个包我并没有能力逐个核实实现细节。桌面那一节的第一版就把 `native-gui` 归成了「原生控件」，实际上它用的是系统渲染引擎，和自带渲染引擎的 `moui` 是两条不同的路——这个错误是包作者指出来才发现的。简介里如果还有与事实不符的地方，欢迎直接指出。

如果你也在用 MoonBit，这份索引应该能省下一些翻 README 的时间。
