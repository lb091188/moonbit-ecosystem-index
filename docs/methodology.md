# 分类与排序规范

本文说明**一个包为什么被分到这个场景、为什么排在这个位置**。数据来源与刷新流程见
[数据来源与更新](data.md)，构建操作见[构建、部署与工作台](maintenance.md)。

这些规则由人工维护，属于本项目的编辑方针而非注册表事实。判断有出入时欢迎提 issue，
**给出包名即可定位规则**：场景判定词（`kw` / `core`）、显式收录（`force` / `pick`）、
排除项（`ex` / `ex_desc` / `ex_prefix`）与整族排除都集中在 `data/scenarios.src.json`，
打分实现在 `app/rank.mbt`。

---

## 一、分层口径

同一场景内混列「可承担项目骨架的包」与「提供单点能力的包」，会使选型失去意义，因此本索引
将候选分为两层；**没有完整方案的场景不设分层**，那里的候选全部是基础库，站内不再分出空的
「完整方案」组。

| 层级 | 判定标准 | 示例 |
| --- | --- | --- |
| **完整方案** | 定义程序结构，由调用方填空：路由表、组件树、事件循环、ECS、数据访问层、命令行树、语法 DSL、测试容器 | `moonback`、`rabbita`、`proton`、`selene`、`moondb`、`ArgParser` |
| **基础库** | 提供单点能力，由调用方组合：格式解析、哈希、C 库绑定、数据结构 | `yaml`、`sha256`、`btree`、`sqlite`、`gtk`、`glfw` |

框架、引擎、运行时、脚手架、ORM 均属「完整方案」的不同形态。

**「基础库」不等同于「依赖」**。在 mooncakes 生态中，完整方案本身同样是依赖
（`moon.mod.json` 的 deps 收录全部包），因此以 deps 作为「方案」的反义词在定义上不成立。
分层的唯一标准是该包能否接管程序结构。由此可推出：所有 binding 均归入基础库，完整方案位于
其上层（`giraffe` 之于 GTK，`proton` 之于 WebView）。

完整方案的判定**采用人工白名单**（`data/scenarios.src.json` 里的 `sol` 收录规则），不使用
启发式推断。方案层是高精度区，宁可遗漏，也不将基础库纳入推荐位。构建日志会输出「待确认的
方案候选」——自我描述含 `framework` 等字样、尚未收录白名单的包，供人工复核后补入；缺简介的
方案包也会列出来，避免补写这件事无声无息地烂掉。

并非每个场景都有完整方案。graphics、img、media、httpc、net、proto、json、binfmt、compiler、
regex、unicode、hash、cipher、encode、archive、fs、math、ds、tool、doc、time、log 等场景在生态中
尚无框架或引擎级实现。这些场景站内只有一个基础库清单，并注明「尚无完整方案，需按需组合」，
不去虚构一个空的方案组。这属于生态现状，而非数据缺失。

## 二、场景粒度与归属

### 粒度：一个开发者的一次决策

场景按「一次决策」划分，而不是按包的实现方式。粗粒度场景无法给出可操作建议：把 JSON、YAML、
CBOR 混在一个清单里，选型时仍要自己逐条筛。因此对原先过粗的场景做了拆分：

| 原场景 | 拆分后 | 依据 |
| --- | --- | --- |
| JSON / 序列化格式 | JSON 解析、配置 / 标记格式、二进制编码 | 文本格式、配置语言、二进制编码是三类不同的选型 |
| 加密 / 哈希 / 编码 | 哈希 / 校验、加密 / 签名、编码 / 转义 | 校验完整性、保证机密性、字节转文本，用途互不替代 |
| 图像 / 媒体 | 图像编解码、音频 / 视频 | 图像处理与音视频播放 / 采集没有交集 |
| 网络 / 协议 | 网络传输 / 套接字、应用协议 / RPC | 传输层选型与协议栈选型是两个问题 |
| Web 后端 / HTTP 服务 | 服务端框架、HTTP 客户端 | 写服务端与调别人接口，候选几乎不重合 |
| 解析器 / 编译器 / 语法 | 解析器 / 语法、编译器 / 代码生成 | 把文本读成结构，与把结构变成可执行物 |
| CLI 参数解析 | 同上（加了 `core` 门控） | 原先候选中大量是「带 CLI 的应用」，收紧后只留真正的命令行库 |

拆分的代价是场景数量变多，但每个清单的可信度更高。合并与拆分都只依赖关键词与人工白名单，
没有引入新的判定机制。

### 归属：覆盖即出现

一个包若同时胜任多个场景，就在每个场景里都出现，不设「主场景」独占。例如 `moui` 既在桌面
（macOS / Windows / Linux 主线）也在移动端，`moonbit-community/pty` 同时出现在终端 UI、异步与
运维三个场景。多数场景由关键词自动判定，因此天然支持多归属；桌面、移动端与运维为人工清单，
需人工维护多归属关系；桌面以关键词判定为主，少数元数据命不中的包由 `force` 显式兜底。

为避免人工清单长期漏收，这类场景声明了 `audit` 复核词，构建时扫描全量模块，命中却未收录的
包会打印成「人工场景的覆盖缺口」；确认不收的包记入 `skip` 并写明理由，使排除决定同样可追溯。

### 方案简介

只有**完整方案**写一句话简介，基础库沿用注册表原描述。基础库的回答是「它提供什么能力」，
注册表已经写了；完整方案的回答是「它替我做了哪些决定、什么时候该选它」，这是注册表不回答、
而选型真正要问的那一层。

简介在 `data/blurbs.json` 人工维护，与代码分离：

```json
{
  "moonbit-community/proton": [
    "类 Electron 的桌面运行时：界面交给内置浏览器承载……",
    "Electron-style desktop runtime: the UI lives in a built-in webview……"
  ]
}
```

- 值是 `[中文, 英文]`，与 `title` / `intro` 同一套取法，前端按语言取下标；
- 以 `_` 开头的键当注释用，不参与构建；
- 改完重新执行一次「数据生成」即可（见[构建、部署与工作台](maintenance.md)），无需改代码；
- **缺简介不拦住构建**（退回原描述），但构建日志会打出覆盖数与缺失清单。

写的时候只回答三件事：这是什么形态的方案、它替你做了什么决定、什么情况下该选它。不要写
「高性能」「强大」这类换任何包都成立的词——那句话对选型没有信息量。

## 三、排序方法

默认权重（`data/build.json` 不存在时用内置缺省，工作台「数据生成」页可改）：

```
score = min(相关度, rel_cap) × rel_w + ln(1 + 下载量) × dl_w
        + (在 pin 中 ? pin_w : 0) + boost(该场景对该包的加权)

缺省：rel_cap=6.0  rel_w=1.0  dl_w=1.35  pin_w=1.2  min_dl=20
```

只使用两项信号：与场景的关键词相关度、注册表内的下载量。**不引入反向依赖数、传递依赖数等
派生指标**——本站只做导航，派生指标既扩大数据滞后面，也容易把「被依赖得多」误当成
「适合这个场景」。

相关度依据 `keywords`、包名词元与描述词元，并做词干前缀归一（使 `async` 命中
"Asynchronous"、`argparse` 命中 `ArgParser`）。易混场景设有排除规则，例如 UI 场景排除 TUI、
文档场景排除 UI 框架；`core` 是必命中门控，`ex_desc` / `ex_prefix` 是描述与包名前缀排除。
相关度低于 3、下载量低于 `min_dl`、或已 yanked 的包不进入推荐。

关键词命不中、但人工确认属于该场景的包记在 `force`，按**其所属层级的中位分**安置：既不因
手工收录而占据前列，也不因描述缺失而沉到末尾；需要更靠前时用 `pin` 或 `boost` 明说。
`top` 用于把清单里靠前的若干条显式抬到前面。

声明了 `pick` 的场景**完全跳过打分**：候选与顺序都由人工清单决定，其 `score` 字段是优先级
序号而非算法得分（桌面、移动端、运维等缺乏稳定关键词的场景走这条路）。

两个容易漏收的边角，已在评分里单独处理：

- **包名精确命中算强信号**。注册表里不少包的关键词与描述都是空的
  （`moonbit-community/yaml`、`moonbit-community/sqlite3`、`Milky2018/gamepad`），名字是唯一
  线索。名字里出现与场景词完全相同的词（长度 ≥3）即按强命中计，但 `net`、`map`、`ui`、`test`
  这类太泛的词列在 `ambiguous_tokens` 里不享受此待遇——`moonxi-net` 是深度学习框架，
  `test_postadd` 是作者的发布探针，都不该因此被收进来。
- **整族排除**。`cli/*`（MoonX 复刻的 coreutils，一条命令一个包）与 `gmlewis/fonts-*`
  （按字母切分的字体数据分片）不进入任何场景：它们的关键词覆盖 command-line / json / hash /
  base64 / svg，会同时污染六七个场景，而单个包并不构成一个可选型的库。

排序是稳定的：同分保持模块表原有顺序，结果可复现。

## 为什么站内不展示下载量

早期版本的每一行右侧都挂着下载量（`7.5k`、`20.1万`），同时在行首标出序号。两个数字并排
出现时，读者必然逐行比对，而序号来自加权分，不可能与下载量同序——**多数场景的区块前几名都
存在「后面的包下载量更高」的情况**。列表因此在最显眼的位置自相矛盾，看起来像排序坏了。

三种处理方式里，最终选择把下载量移出对外产物：

| 方案 | 结果 |
| --- | --- |
| 全员改为按下载量排序 | 名次与下载量恒等，但多个区块会被 `mizchi/x`、`moonbitlang/x` 这类万能包占据第一，`moonback`、`rabbita` 等会掉出前列 |
| 保留加权序、去掉序号 | 不再自相矛盾，但顺序仍无法被读者核验 |
| **下载量只在构建期排序，不进产物**（当前） | 顺序保留推荐质量，页面上不存在第二个数字，无从比对；`scenarios.json` 里也没有这个字段 |

因此：站点数据只有一份事实性来源（模块元数据），下载量退化为一个不公开的量级因子。前端拿不到
任何**单包**的下载量，也就没有再次把「流行」误读成「适合」的可能。选型要看的是 API 形态与
维护状态，这两项本就该到包页自行核对。

唯一的例外是首页「生态增长」里的**全生态累计下载总量**：它是一个随时间变化的汇总，不与任何
一行绑定、不参与排序，也无法拿来逐包比对，因此不构成上面说的自相矛盾。单包数字依旧不进
`dist/`。检索页同理：结果按命中程度排序（包名全等 > 包名开头 > 包名包含 > 描述包含），
同程度按名称排列，不掺任何隐藏权重。

## 四、已知局限

1. **排序含有一个本站不展示的量级因子**：下载量为累计值，不反映近期热度，发布较早的包在
   同等相关度下天然占优。该因子只影响顺序、不出现在页面上，读者无法逐行核验，这是为提高
   推荐质量而做的取舍；可核验的部分是场景归属、层级划分与包页链接。
2. **部分包无描述、无关键词**，仅能依据包名匹配，存在遗漏可能。
3. **场景划分为人为定义**，并非生态固有分类；同一包可能适用于多个场景。
4. **完整方案判定为主观白名单**，边界情形（如 `mizchi/tui` 计入方案而 `tonyfettes/xml`
   不计入）存在判断空间。代价是新发布的方案需人工补入方可出现在方案层。
5. **基础库层未再细分**，目前未区分完整工具（如 `cmark`）与底层原语（如 `sha256`）。
6. **桌面与移动端两个场景为人工圈定**：生态中既没有 `desktop` / `mobile` 这种可靠关键词
   （`mobile` 会被三端窗口库命中，`ios` 会命中 `versions`），也无法靠描述区分，因此候选清单
   与顺序由人工确定。多归属关系同属人工维护，靠构建时的 `audit` 复核词兜底提示。
7. **运维场景为人工圈定**：生态中的运维能力分散在伪终端、子进程、系统指标等单点库里，
   没有框架级实现；进程管理器与 CI 运行器属可整件部署的成品，单列为完整方案，其余按基础库
   列出供组合。
8. **部分场景基础库候选偏多**（wasm、parser、fs、graphics 等关键词宽泛的场景），未做进一步
   收敛；详情页完整列出，首页仅显示前几个。
9. **`moonbit-community/window` 在注册表中已不可用**，现行为 fork 版 `wzzc-dev/window`；
   `Milky2018/window` 为另一条独立实现。
10. **`Yoorkin/rabbit-tea` 已被 yanked**，TEA 路线的现行实现为 `moonbit-community/rabbita`。
11. **新包在排序中系统性偏弱**：`ln(下载量)` 权重最高，而下载量为累计值，刚发布的包难以与
    老包比较。`created_at` 系注册表收录时间而非项目起始时间，无法据以计算增长速度，因此只能
    对部分框架级包（`proton`、`moui`、`native-gui`）人工加权。该偏差只体现在顺序上，站内不
    展示下载量，读者不会被一个数字误导；但顺序本身确实带有这个偏好。
